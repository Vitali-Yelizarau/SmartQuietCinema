# Virtual Audio Static Analysis

This review covers the experimental render-only x64 driver at pinned Microsoft SysVAD revision `d49bb7d72f3651952b2b6e4ad28d14fe2247eb69`. The baseline was SmartQuietCinema commit `80cd71003be74492f8be12e571d436456bdf5142` with the v3 adaptation. The reviewed fixes are staged by `Prepare-SysVad.ps1` v4. The diagnostic paths and line numbers below are relative to the staged `audio/sysvad` directory. The driver has not been exercised in a VM. **Runtime status: Not yet validated.**

## Reproduce the analysis

Prepare SysVAD as described in the [driver README](README.md). In the matching WDK developer shell, build a fresh Debug x64 configuration with SDK `10.0.28000.0`. Use a fresh intermediate directory for each comparison so all translation units are analyzed. Preserve the full MSBuild log.

```powershell
$analysisRoot = Join-Path $env:TEMP ('sqc-wdk-analysis-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $analysisRoot | Out-Null
MSBuild.exe .\SmartQuietCinema.Driver.VirtualAudio\SmartQuietCinema.VirtualAudio.vcxproj /t:Build /p:Configuration=Debug /p:Platform=x64 /p:WindowsTargetPlatformVersion=10.0.28000.0 /p:RunCodeAnalysis=true "/p:IntDir=$analysisRoot\obj/" "/p:OutDir=$analysisRoot\bin/" "/flp:LogFile=$analysisRoot\driver.log;Verbosity=Normal"
```

The verified toolchain was MSVC `14.52.37025` with WDK `10.0.28000.3231`. Both passes used `DriverMinimumRules.ruleset`, MSVC `EspXEngine.dll`, and the SDK 28000 `WindowsPrefast.dll` and `drivers.dll` plug-ins. Deduplicate the repeated MSBuild summary by diagnostic, source, location, and reported identifier. Account for shifted lines in adapted files. The comparison found **99 → 93 unique warnings**, six removals and zero additions. All reported locations are inherited SysVAD. The project-owned endpoint table and the managed builds emitted zero warnings.

## Diagnostic registry

### Registry adaptation

The INF binds the two interfaces directly by the names in `VirtualRender`. The endpoint descriptor has null `TemplateTopoName` and `TemplateWaveName` fields. `InstallEndpointFilters` passes those fields to `InstallSubdevice`, and `CreateAudioInterfaceWithProperties` enters template migration only for a non-null template reference string. The registry-copy defects are real failure-path defects in the inherited code. The current endpoint leaves that feature inactive.

### Inherited PortCls annotation distinction

The previous adaptation removed the demonstration that temporarily registered the PnP start thread. The two corresponding `ResourceSet` diagnostics are absent from both runs. Microsoft's two stream resource manager methods require `NULL` for this reserved argument. This does not carry over to `IPort::Init`: the inherited `InstallSubdevice` contains a narrowly scoped C6387 pragma for `ResourceList`. The current topology and WaveRT calls supply null, and the official `IPort::Init` documentation does not explicitly mark that argument optional. The ordinary build, static analyzer, and INF validation cannot establish that PortCls accepts this on the target runtime. **Not yet validated.** [AddStreamResource](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iportclsstreamresourcemanager-addstreamresource) · [AddStreamResource2](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iportclsstreamresourcemanager2-addstreamresource2) · [IPort::Init](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iport-init)

## WaveRT ownership and notification ordering

- The WaveRT stream holds a reference to its miniport after `Init` succeeds in acquiring it. The port stream interface is stored for buffer operations. `AllocateBufferWithNotification` requests pages and maps them through that interface. The paired free method unmaps the cached address before releasing the MDL pages. These are PortCls buffer operations, distinct from the stream's pool-backed format and level arrays.
- `SetState` is pageable. RUN arms the software timer when notification is enabled. The documented RUN → PAUSE → ACQUIRE → STOP sequence encounters the timer cancellation and DPC flush in PAUSE. `TimerNotifyRT` executes at `DISPATCH_LEVEL`, takes `m_PositionSpinLock` and accesses the stream, miniport, and registered events. Keep that path nonpageable and free of blocking work. [SetState](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iminiportwavertstream-setstate) · [Timer deletion semantics](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/deleting-a-system-allocated-timer-object)
- The miniport stores a PortCls-supplied `PKEVENT` in its own nonpaged list entry. `UnregisterNotificationEvent` removes and frees that entry. These pageable mutators do not take `m_PositionSpinLock`, while the callback iterates the list with it held. The documented client sequence unregisters events after stopping and before closing. Unexpected overlap or teardown ordering is a potential high-severity lifetime risk. The stream destructor releases some resources before `ExDeleteTimer(..., TRUE, TRUE, ...)`, which waits for outstanding callbacks. Verify stop, notification cleanup and surprise removal ordering in the isolated VM before drawing a runtime conclusion or changing synchronization. **Not yet validated.** [Register notification event property](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/ksproperty-rtaudio-register-notification-event) · [UnregisterNotificationEvent](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iminiportwavertstreamnotification-unregisternotificationevent)
