# Virtual Audio Static Analysis

This review covers the experimental render-only x64 driver at pinned Microsoft SysVAD revision `d49bb7d72f3651952b2b6e4ad28d14fe2247eb69`. The baseline was SmartQuietCinema commit `80cd71003be74492f8be12e571d436456bdf5142` with the v3 adaptation. The previous audit fixes are staged by `Prepare-SysVad.ps1` v4. The Hyper-V preflight applies the additional v5 adaptation to that baseline. The diagnostic paths and line numbers below are relative to the staged `audio/sysvad` directory. The driver has not been exercised in a VM. **Runtime status: Not yet validated.**

## Reproduce the analysis

Prepare SysVAD as described in the [driver README](README.md). In the matching WDK developer shell, build a fresh Debug x64 configuration with SDK `10.0.28000.0`. Use a fresh intermediate directory for each comparison so all translation units are analyzed. Preserve the full MSBuild log.

```powershell
$analysisRoot = Join-Path $env:TEMP ('sqc-wdk-analysis-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $analysisRoot | Out-Null
MSBuild.exe .\SmartQuietCinema.Driver.VirtualAudio\SmartQuietCinema.VirtualAudio.vcxproj /t:Build /p:Configuration=Debug /p:Platform=x64 /p:WindowsTargetPlatformVersion=10.0.28000.0 /p:RunCodeAnalysis=true "/p:IntDir=$analysisRoot\obj/" "/p:OutDir=$analysisRoot\bin/" "/flp:LogFile=$analysisRoot\driver.log;Verbosity=Normal"
```

The verified toolchain was MSVC `14.52.37025` with WDK `10.0.28000.3231`. Both passes used `DriverMinimumRules.ruleset`, MSVC `EspXEngine.dll`, and the SDK 28000 `WindowsPrefast.dll` and `drivers.dll` plug-ins. Deduplicate the repeated MSBuild summary by diagnostic, source, location, and reported identifier. Account for shifted lines in adapted files. The prior audit found **99 → 93 unique warnings**. The preflight compared the v4 and v5 staging trees with the same rules and found **93 → 90**, three removals and zero additions. All reported locations are inherited SysVAD. The project-owned endpoint table and the managed builds emitted zero warnings.

## Diagnostic registry

### Registry adaptation

The INF binds the two interfaces directly by the names in `VirtualRender`. The endpoint descriptor has null `TemplateTopoName` and `TemplateWaveName` fields. `InstallEndpointFilters` passes those fields to `InstallSubdevice`, and `CreateAudioInterfaceWithProperties` enters template migration only for a non-null template reference string. The registry-copy defects are real failure-path defects in the inherited code. The current endpoint leaves that feature inactive.

### Inherited audio-module helpers

`VirtualRender` has a zero `ModuleListCount` and a null `ModuleList`. `VirtualWaveAutomation` exposes pin format proposals. It does not publish the audio-module property set. `CMiniportWaveRT::Init` skips the module array, `AllocStreamAudioModules` returns an empty list, and `AudioModule_GenericHandler_ModuleCommand` returns `STATUS_INVALID_DEVICE_REQUEST` for a null or empty list before invoking a descriptor. The inherited helpers remain compiled. The dormant demonstration call path begins at the module property handlers in the WaveRT miniport or stream, checks the module list in `AudioModule_GenericHandler_ModuleCommand`, then calls an explicitly registered descriptor. Demo descriptor handlers such as `AudioModule0_Handler` validate the command header and pass the value and output length to the generic helpers. The active render descriptor has neither the module property entries nor module instances required to take this path.

In this build `NewAdapterCommon`, `InstallSubdevice`/`CreateMiniportWaveRTSYSVAD`, and `CMiniportWaveRT::NewStream` use `POOL_FLAG_NON_PAGED`, without `POOL_FLAG_UNINITIALIZED`. ### PortCls startup resource list

The older static render path discarded the `PCPFNSTARTDEVICE` callback's `PRESOURCELIST` argument. `InstallAllRenderFilters` called `InstallEndpointRenderFilters`, then `InstallEndpointFilters` supplied null to both topology and WaveRT `InstallSubdevice` calls. These converge at the single `IPort::Init` call. WDK 28000 marks that argument `_In_` and the public contract identifies it as the list supplied at start. Our miniports do not consume hardware DMA or interrupt descriptors. PortCls may inspect the list even when it contains zero entries. A null pointer violated the declared contract. Whether the older package would reject it, fault, or happen to accept it is **Not yet validated**. [PortCls startup sequence](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/startup-sequence) · [IPort::Init](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iport-init)

v5 checks the callback input before creating the adapter and forwards the borrowed object to both ports. No private list is fabricated or retained by the adaptation. The operating system provides the list, and the COM reference rules apply to PortCls and miniports. `PcNewResourceList` is for callers with WDM-provided raw and translated resource lists and is unnecessary here. The scoped C6387 suppression at `IPort::Init` was removed. A topology-installation error crosses no later wave call and a failed wave installation crosses no connection call. The old code could overwrite a topology or cache-insertion failure with a later success. The unused sideband call sites have no start resource list and do not gain support from this change. The older `AddStreamResource` demo removal involved a different parameter, `ResourceSet`, that Microsoft explicitly reserves as null. [PcNewResourceList](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-pcnewresourcelist) · [AddStreamResource](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iportclsstreamresourcemanager-addstreamresource)

## WaveRT ownership and notification ordering

- `NewStream` keeps the output unpublished on failure. `Init` sets the notification list and spin lock before the first fallible timer allocation. It takes a miniport reference when available, and records whether `StreamCreated` succeeded so partial cleanup does not close an unregistered stream. A timer is allocated before format and level arrays but only armed after a successful transition to RUN. The destructor deletes the timer with cancel and wait before touching callback-reachable resources or any leftover event nodes. It does not hold the spin lock while waiting. The destructor's DPC flush requires `PASSIVE_LEVEL`. [ExDeleteTimer](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-exdeletetimer) · [KeFlushQueuedDpcs](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-keflushqueueddpcs)
- PortCls supplies the mapped `KEVENT` pointer. The stream owns the nonpaged list node, while it borrows the event pointer until unregistration. The timer's list traversal and both mutators share `m_PositionSpinLock`. List removal and pool release are separate operations, and allocation and free occur at the caller's IRQL. Code that executes while the spin lock raises IRQL is resident. `TimerNotifyRT` runs at `DISPATCH_LEVEL` and returns before accessing positions or the miniport when state is outside RUN or the buffer/notification count has been cleared. [RegisterNotificationEvent](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iminiportwavertstreamnotification-registernotificationevent) · [UnregisterNotificationEvent](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iminiportwavertstreamnotification-unregisternotificationevent)
- STOP disarms the timer and resets counters under the position lock. ACQUIRE does not arm it. RUN initializes the performance-counter state and checks that a buffer exists before arming. PAUSE retains cancellation and the DPC flush, then publishes the final state under the same lock. The flush only guarantees DPCs already queued at entry. Final destruction uses the timer API with wait to close that gap. Preserve the documented STOP → ACQUIRE → PAUSE → RUN transition and its reverse. [SetState](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iminiportwavertstream-setstate) · [ExCancelTimer](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-excanceltimer)
- Both buffer allocation methods free their MDL on a null mapping and return resources failure without publishing success. The notification path checks divisibility after frame alignment and rejects intervals below the timer's whole-millisecond resolution. It uses wide arithmetic before dividing to avoid overflow at the supported rates. PortCls retains responsibility for calling the matching free method. That method disconnects buffer state under the position lock before unmapping and freeing pages at `PASSIVE_LEVEL`. Position updates skip the zero-size buffer. [MapAllocatedPages](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-iportwavertstream-mapallocatedpages) · [WaveRT rebalance and surprise removal](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/managing-memory-buffers-rebalance)
- **PnP preflight blocker.** `IRP_MN_STOP_DEVICE`, `IRP_MN_SURPRISE_REMOVAL`, and `IRP_MN_REMOVE_DEVICE` run adapter cleanup, release the extension's common-adapter reference, and then invoke `PcDispatchIrp`. Cleanup empties the adapter's subdevice cache. The WaveRT miniport's adapter pointer is weak, and open streams can still reach it through ETW calls. The available power-manager contract does not establish how long PortCls retains the registered adapter across shutdown. The separate lifetime of an already open stream therefore does not prove the lifetime of its adapter. The public WaveRT removal model allows outstanding stream handles to outlive device removal. The local timer and list changes do not establish a PnP-wide quiescence or reference guarantee. Treat active-stream removal, restart and the associated partial-start cleanup as **Not yet validated**. Resolve the ownership and quiescence contract before authorizing a first unrestricted guest trial. The return code or behavior of PortCls after surprise removal has not been exercised. [WaveRT removal and close ordering](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/managing-memory-buffers-rebalance) · [PcRegisterAdapterPowerManagement](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-pcregisteradapterpowermanagement)

## Verification coverage

Two independent v4 preparations under Windows PowerShell 5.1 produced the same SHA-256 manifest for all 189 staged files. Relative to v3, only `common.cpp` and the stamp changed. The matching WDK builds produced INF, SYS, and CAT. `InfVerif /u` accepted the INF. Ten user-mode checks used the extracted v4 functions and mocked kernel services to check normal copying, allocation and enumeration failure, handle cleanup, registration status and start retry. These tests exercise branching and ownership with no live PortCls or registry activity. Driver installation, PnP failure recovery, timer/notification teardown, and actual PCM transfer remain **Not yet validated**.

Two independent v5 preparations produced identical SHA-256 manifests for all 189 staged files. The source delta touches only `adapter.cpp`, `common.h`, `common.cpp`, `AudioModuleHelper.cpp`, and `minwavertstream.cpp`, plus the stamp. The ordinary Debug x64 build had no warnings, the INF passed `InfVerif /u`, and the WDK analyzer produced the 90 diagnostics above. Twelve v5 user-mode checks ran extracted functions with mocked DDIs. They cover page allocation and mapping failures, interval validation, buffer release ordering, duplicate and failed event registration, timer-before-reference destruction, and module output validation. The ten v4 registry and factory failure checks also passed against v5. These checks do not exercise concurrent kernel callbacks, live PortCls, or restart. The actual guest, package signature acceptance, device installation, and audio playback remain **Not yet validated**.
